## Part 1 — Per-system

### System 1 — Agentic loop

1. **Loop control.** Quote the `stop_reason` sequence from one trace. Name the file and function that decides continue-vs-stop, and how.
   → `submission/system1/run_20261017_112857/traces/claim_03_water_damage.jsonl` shows `t1 tool_use [lookup_policy] → t2 tool_use [record_claim_fact ×3, request_clarification] → t3 tool_use [record_claim_fact, request_clarification] → t4 tool_use [classify_claim, assess_severity] → t5 tool_use [route_to_adjuster] → t6 end_turn`. Continue-vs-stop is decided in `claims_intake/loop.py`, function `run()`. Inside a bare `while True:`, a `tool_use` response executes every tool block, appends the `tool_result`s and `continue`s. An `end_turn` response appends the assistant turn and `return`s a `FinalState`. Any other value raises `UnexpectedStopReason`. Nothing else ends the loop except `Budget.check()`, which raises `BudgetExceeded` (defaults 500,000 input tokens / 180 s in `run.py`). The loop never inspects the assistant's text.

2. **Anti-pattern.** Name one anti-pattern `test_antipatterns.py` checks for. What would break in your run if the loop used it?
   → `test_no_integer_literal_iteration_cap_in_loop` uses the AST to reject `for _ in range(<int>)` and `while turn < <int>` in `loop.py`. My run shows why. Claim turn counts in `summary.md` range from 2 to 6, and claim_03 only reached `route_to_adjuster` on turn 5 and `end_turn` on turn 6. A cap of 5 would have dropped its closing turn. A cap of 3 would have cut it off right after the second `request_clarification`, before `classify_claim`, so no queue record would ever have been written. Either way the loop would have exited "successfully" with an unfinished claim, and nothing would have flagged it. A budget raises an error instead of truncating silently.

3. **Tool design.** Pick two tools with overlapping inputs. How do the descriptions prevent misrouting? What did a structured tool error let the agent do that a generic string would not?
   → `route_to_adjuster` and `escalate_to_human` (`claims_intake/tools.py`) are both "TERMINAL TOOL"s that end a claim with a summary of the case. Their descriptions split on the same threshold: route "when classification confidence is at least 0.6 and severity has been assessed", escalate "when classification confidence is below 0.6 even after clarification". `route_to_adjuster.queue` is an enum of the four claim types, so the queue can't be misspelled. Errors are JSON `{is_error, error_category, is_retryable, message}` from `_err()`. For example, routing before classification returns `permanent / not retryable / "classify_claim must be called before routing"`, which tells the model exactly which missing step to take rather than to retry. The same goes for `"terminal tool already called this claim"`, which stops a double terminal call (tests `test_routing_requires_classification_and_severity`, `test_double_terminal_is_graceful_error`). In my run the model always called `classify_claim` + `assess_severity` before routing (claim_03 t4 → t5, claim_05 t2 → t3), so these guards were never hit live. A generic string like `"error"` would give the model no idea whether to fix its input, retry, or stop.

4. **Your numbers.** Quote the turn count and cost for one claim. How does it differ from the README sample, and why?
   → `claim_05_auto_collision`: 4 turns, 14,841 input / 906 output tokens, $0.0194, routed `auto` / `high`. The exercise README expects "7 routed, 1 escalated" at about $0.05 for all 8 claims. My run got **4 routed, 4 escalated** for **$0.1269**. The difference comes from the model: on claims 01, 02, 06 and 07 Haiku returned `end_turn` without calling a terminal tool, after only 1–2 turns. The deterministic backstop then escalated them (`escalations.jsonl`: `"model ended its turn without a terminal action (deterministic backstop)"`). Cost is dominated by input tokens (97,314 input vs 5,911 output in total), because every turn resends the system prompt, the seven tool schemas and the growing message list. Claim_03 alone used 21,952 input tokens over 6 turns. Claim_04 also came out `medium` where the fixture expects `high`, which shows that outputs from a live model vary from the reference run.

### System 2 — Context strategy

5. **The reduction.** From `budget.json`: baseline tokens, assembled tokens, reduction %. Which section dominates the assembled context, and why keep it verbatim?
   → From `submission/system2/budget.json` (run `20261017-115417`, counted with the Anthropic `count_tokens` endpoint): baseline **38,708** tokens, assembled **16,848**, a **56.47 %** reduction, above the 50 % target. The `active` section dominates at 15,789 tokens (≈ 94 % of the assembled context), compared with case_facts 204, resolved_refund 396 and resolved_subscription 477. It stays byte-exact because it is the issue still being worked. Q3 (`AVS_MISMATCH`) and Q4 (`7782`) are answered from those live turns, and a summary could round, paraphrase or drop the exact token the next reply needs. `test_assembled_context_active_segment_byte_exact` enforces this, and `assemble.py` places the section at the bottom, next to the incoming user turn.

6. **Summarize vs preserve.** State the rule for what gets summarized vs kept byte-exact, citing your per-section token numbers.
   → The rule: segments with status `resolved` are summarized, the active segment is never summarized, and transactional facts are pulled out into a structured block. `compressor.summarize_segment` raises `ValueError` for anything that isn't `resolved` (`test_summarize_segment_refuses_to_compress_the_active_segment`). In my run the refund segment went from 12,334 input tokens to a 396-token summary, and the subscription segment from 11,475 to 477, a ~30× reduction on finished history. The 12 transactional fields (IDs, amounts, status tokens) were extracted once into a 204-token Case Facts block at the top (`case_facts_call.json`: e.g. `refund_amount_usd: 22.14`, `payment_update_status: in_progress`). The active payment-update segment stayed verbatim at 15,789 tokens. In short: compress what is finished, keep exact what is live, and pin exact identifiers somewhere compression can't touch.

7. **Facts block.** Compare `eval.jsonl` to `eval_control.jsonl`. Which question regressed, and what does that prove?
   → With the full context `eval.jsonl` passed **6 / 6**. The control with Case Facts stripped (`eval_control.jsonl`) regressed on **Q6**. The full run answered "`payment_update_status`: in_progress". The control answered "there is no structured status token recorded… No status token is present in the provided context". Q1 ($22.14) still passed, because that amount also survives in the refund summary. So `eval_metrics.txt` records `control_failed_or_regressed: 1 / 2`. This proves the Case Facts block carries real weight: the snake_case status token for the *active* issue exists only in the facts block, not as an exact token in the 15,789-token verbatim narrative. Without the block the model can't recover it, even though the raw turns are all present. (The earlier run `20261017-115158`, logged in `full_run.txt`, shows the same result: 6/6 full, Q6 regressed in control.)

### System 3 — Claude Code config

8. **Path-scoped rules.** Quote the glob frontmatter from one rule file. Why is it better than a directory-level CLAUDE.md for cross-cutting conventions?
   → `.claude/rules/tests.md` declares `paths: ["**/*.test.tsx", "**/*.test.ts"]` (see `submission/system3/config_structure.txt`). Tests are co-located with source, e.g. `src/components/Cart/Cart.test.tsx` next to `Cart.tsx`, so there is no single "tests directory" for a directory-level CLAUDE.md to sit in. It would have to be copied into every folder that contains a test, and the copies would drift apart. A glob matches by file shape anywhere in the tree and stacks with other rules: `test_ac_02_06_test_file_matches_react_and_tests` confirms that a React test file loads both `react.md` and `tests.md`, and `test_ac_02_05_api_file_matches_only_api_rule` confirms that an API file loads only `api.md`. The rule also loads only when a matching file is being edited, so it costs no context in other sessions.

9. **Forked skill.** Quote the `context: fork` and `allowed-tools` lines. What does running forked + read-only buy you? What breaks without it?
   → `.claude/skills/deploy-check/SKILL.md` declares `context: fork` and `allowed-tools: [Read, Grep, Glob, Bash(git status:*), Bash(git diff:*), Bash(git log:*), Bash(git rev-parse:*), Bash(git ls-files:*), Bash(gh pr view:*), Bash(gh pr checks:*)]`. Running forked keeps the verbose output (file enumeration, raw `git status`, diff hunks, CI logs) inside the sub-agent, and only the fixed `verdict / checks` summary returns to the main session. The read-only allowlist means a pre-deploy *check* can't change what it is checking: no `Edit`, `Write`, bare `Bash`, `git push` or deploy. `test_ac_04_03_allowed_tools_read_only` and the validator's `write_capable_tools` check enforce this. Without the fork, every `/deploy-check` would flood the developer's working context with throwaway output. Without the allowlist, the "check" could fix things or push on its own, so a pass would no longer mean the branch was actually clean.

10. **Scope.** From the validator output: project-level vs user-level scope. Give one example of each from this config.
    → `python -m ecommerce_team_config .` printed `OK` with exit code 0 (`submission/system3/validator.txt`). One of its checks, `distinguishes_project_vs_user_scope`, requires CLAUDE.md to spell out the two scopes. **Project-level** means versioned and shared with the team: `./CLAUDE.md` with its four `@.claude/standards/*.md` imports, `.claude/rules/*.md`, the `/review` command in `.claude/commands/review.md`, and the `deploy-check` skill. **User-level** means `~/.claude/`, never committed and private to one developer: the SKILL.md suggests a stricter personal variant at `~/.claude/skills/deploy-check-strict/`, and CLAUDE.md gives a personal `/morning` command as an example. When a convention isn't being followed, CLAUDE.md points to `/memory` to see which files actually loaded.

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
    → The warm tier held **40** defects. For the run window `--since 2026-04-22T00:00:00Z` the SQL query returned **4** (`DEF-20260429-001`, `-0427-001`, `-0425-001`, `-0423-001`), and the run printed `shift C: 4 new defects` (`submission/system4/shift_run.txt`). The query is `WarmStore.defects_since()`: `SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?`. Its `EXPLAIN QUERY PLAN` in my run shows `SEARCH defects USING INDEX idx_defects_ts (ts>?)`. `pipeline.gather_new_defects` passes rows through with no Python-side filtering (`test_gather_new_defects_has_no_python_side_filtering`). The model gets only the hot state plus this slice, and `test_build_rich_prompt_stays_under_4000_chars` keeps the prompt bounded. The system runs every 8 hours indefinitely, so sending the full history would grow every prompt forever, making it costlier and burying the newest defects among old ones. Filtering is deterministic work, so SQL does it, and the model is used only for judgment.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?
    → `recovery.decide()` returns `fresh` if the manifest has no steps or is already `complete`. It returns `resume` only if the last step's timestamp is within `STALE_RESUME_THRESHOLD_MINUTES = 30` of now, and `fresh` otherwise. The 30 minutes is about 1/16 of an 8-hour shift: inside that window the partial run is still working on the same shift's data. The truth-table tests in `submission/system4/pytest.txt` pin the boundary: 1, 29 and 30 minutes → `resume`; 31 → `fresh`; a completed manifest → `fresh` even at 1 minute. A stale partial run carries reasoning based on a hot state and defect slice that newer data has already superseded. Resuming it would make the model reconcile outdated partial conclusions against new facts. A fresh start through `invocation.resumed()` instead injects the prior steps (each payload truncated to 120 characters), the summary, and only the defects since the last step. That gives the model a small, consistent prompt instead of an inconsistent one. Manifest writes are append-only with `fsync` (`test_append_step_writes_and_fsyncs`), so a crash mid-write still leaves the earlier complete lines readable (`test_mid_write_read_reveals_prior_complete_lines`).

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?
    → After the shift C run, `submission/system4/hot_state.json` is **718 bytes**, against `HOT_STATE_BYTE_BUDGET = 5,120` in `state.py`. It holds 4 defect hashes (capped at `MAX_RECENT_HASHES = 20`), a one-line summary, 3 alerts and 3 threshold statuses. The hot state goes into *every* prompt, three times a day, with no end date. Without a hard cap, alerts and hashes would pile up shift after shift until the state crowded out the new defects it exists to frame. So the cap is enforced in code: `pipeline._trim_to_budget` drops alerts until the state fits, and `HotState.write_atomic` raises if the payload is still over budget, then writes via temp file + `fsync` + `os.replace`, so a crash can't leave a half-written state. Forks reuse the same small state: in `submission/system4/fork_run.txt`, `fork_for_hypothesis` copied it into `data/forks/H1-lot-dielectric/` and `data/forks/H2-station-drift/`. Each fork wrote only to its own `scratchpad.jsonl` (`H1 scratchpad sees H2 entry? False`, and the reverse is also False). The base `hot_state.json` hash stayed `c6a2b6f88d78e1e4` throughout. The main scratchpad stayed at 1 entry until an explicit `merge_findings()` appended both, giving 3 entries (`shift_scratchpad_after_merge.jsonl`).

15. **Deterministic vs prompt.** Cite one behavior guaranteed in code (terminal tool, read-only allowlist, atomic write, byte budget) and one guided by prompt. When is each right?
    → **Guided by the prompt:** System 1's `SYSTEM_PROMPT` (`claims_intake/system_prompt.py`) tells the model to "Choose exactly one terminal action" and, only "After your terminal tool call", to confirm and stop. **Guaranteed in code:** `run.py`'s `_escalate_without_terminal` backstop, which escalates any claim that hits `end_turn` without `session.terminal_called`. My run is direct evidence that both are needed. The prompt alone failed on 4 of 8 claims (01, 02, 06, 07 in `escalations.jsonl`), and the code made sure every claim still ended routed or escalated. Other code guarantees in these projects: the read-only `allowed-tools` on `deploy-check` (System 3), and `HotState.write_atomic`'s 5,120-byte cap plus `os.replace` (System 4). Prompt guidance is the right tool for judgment calls that can't be listed in advance, such as what counts as "genuinely ambiguous" or which severity bucket a mixed injury fits. Use code whenever a violation would be unsafe, corrupt state, or break an invariant that downstream systems rely on: every claim terminates, a checker never writes, state never exceeds its budget.

16. **Context, two faces.** Compare context management in System 2 (intra-session) and System 4 (cross-session) with cited numbers from both. Same principle, different mechanism — how?
    → Both follow the same principle: give the model only what the next decision needs, with exact facts pinned where nothing can blur them. **System 2 (within a session)** shrinks a single long conversation. It went from 38,708 to 16,848 tokens (−56.47 %) by LLM-summarizing resolved history (12,334 → 396 and 11,475 → 477 tokens), keeping the live issue verbatim (15,789 tokens), and pinning 12 fields in a 204-token Case Facts block. The control run proved that block necessary (Q6 regressed). **System 4 (across sessions)** never builds a long context at all. Each shift starts from a 718-byte hot state (budget 5,120) plus a SQL slice (4 of 40 defects through `idx_defects_ts`), so the prompt stays under 4,000 characters (`test_build_rich_prompt_stays_under_4000_chars`). The older history stays in the warm SQLite tier and in deterministic monthly cold summaries (`cold.py`). The difference in mechanism: System 2 *compresses after the fact* with model calls and verifies the result with evals. System 4 *selects before the call* with deterministic code (SQL, a byte cap, a hash cap), so its context size doesn't depend on model behavior. System 2's Case Facts block and System 4's `hot_state.json` play the same role: a small structured record of what is true right now, placed where the model reads it first.

17. **Reliability you can't see in one run.** Name one behavior a test guarantees that a single successful run would not reveal. Why does it matter before shipping?
    → `tests/test_run_backstop.py::test_claim_without_terminal_tool_is_escalated` (System 1) guarantees that a claim whose model says "Thanks, I have everything I need" and stops with `end_turn` still produces an `escalations.jsonl` record. A single successful run such as claim_05 (route at turn 3, `end_turn` at turn 4) never takes that path, so looking at it would tell you nothing about the failure case. In my live run the path fired on 4 of 8 claims. Without the test-backed backstop those claims would have finished with no queue record and no escalation, silently dropped. Another example is System 4's `test_recovery_decide_truth_table`. It pins the exact 30 → 31-minute boundary, which no normal shift run ever crosses because a normal run never crashes. Before shipping, these rare paths are where the real damage happens (lost claims, wrong resume decisions), and tests are the only cheap way to exercise them on purpose.

18. **Blast radius.** Pick one system. What's the blast radius if it misbehaves, and what's the kill switch? Ground it in that system's tools, enforcement points, and state.
    → **System 1.** Its only side effects are appending JSONL to `runs/<ts>/queues/<type>.jsonl` and `runs/<ts>/escalations.jsonl`. It can't pay, deny, or contact anyone. The worst realistic failure is a *wrong* route: a claim sent to the wrong adjuster queue, or a correct queue with the wrong priority. My run shows exactly that: claim_04 (third-party injury) was routed `liability` / `medium` where the fixture expects `high`, so a real injury claim would have been under-prioritized. The harness limits the damage. Queue names are enum-validated. `_t_route_to_adjuster` refuses to route without `classify_claim` and `assess_severity`. `session.terminal_called` blocks a second terminal call, so one claim can't land in two places. Low confidence (< 0.6) is told to escalate. Every turn is traced, so a bad route can be found and replayed. Kill switches: `Budget` (`--max-input-tokens` 500,000, `--max-wall-clock-s` 180) raises `BudgetExceeded` on a runaway claim, and `UnexpectedStopReason` stops the loop on anything other than `tool_use` / `end_turn`. Removing `route_to_adjuster` from `TOOL_SCHEMAS` would leave escalation as the only terminal tool and send every claim to a human. Because each run writes into its own `runs/<timestamp>/` folder, rollback just means discarding that folder.

20. **What you'd change.** One architectural decision you'd make differently, grounded in what you observed.
    → In System 1, I would stop treating `end_turn` without a terminal tool as final on the first occurrence. In run `20261017_112857` four claims (01, 02, 06, 07) stopped after 1–2 turns without routing or escalating. Three of them (01, 02, 07) were expected to be *routed*, and the facts recorded on turn 1 were enough to route them. The backstop correctly kept them from being lost, but it sent routable claims to a human with `confidence: 0.0` and the generic reason "no terminal tool called". That costs reviewer time and drops the model's partial work. I would keep the loop contract as it is (`end_turn` still returns), and in `run.py` give the model one corrective turn when no terminal tool was called: `"You must call route_to_adjuster or escalate_to_human"`, with `tool_choice` restricted to those two tools. The deterministic escalation would still apply if that second attempt also fails. This keeps the code guarantee from Q15 and stops a single model stall from turning into a human escalation.
